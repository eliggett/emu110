# U-110 amplitude envelope, measured from hardware

Generated by `tools/envelope_measure.py`. Raw per-period values are in `envelope_data.csv` next to this file.

## Method

The problem with reading an envelope straight off a note is that the wave-ROM sample has
its own decay baked in, so what you measure is (sample decay) x (chip envelope) and the
two cannot be separated.  This tool removes the sample data from the measurement:

  1. Take the voice parameters the firmware actually wrote to IC15 -- start, end, loop,
     step, volume -- from a MAME register trace.  These are ground truth; the driver just
     forwards what the CPU writes.
  2. Render those voices in Python with NO envelope at all: float8 decode, linear
     interpolation, loop from `end` back to `loop`, partials summed with the logarithmic
     gain from reg 07.  Run the Fig. 4 reconstruction filter over it and resample to the
     capture rate.  Call this the "dry" reference.
  3. Align the dry reference to the hardware note by cross-correlation.
  4. envelope(t) = hardware_peak(t) / dry_peak(t), measured per period of the note's
     fundamental so the measurement window is always a whole number of cycles.

Whatever is left in that ratio is the chip's doing, because everything else -- the sample's
own decay, the multisample choice, the two partials' relative level, the output filter --
is present identically in both.

Use listen/2, not listen/1: listen/1 peaks at 0.9999 with 16 clipped samples, which flattens
every attack in it.

Specifics of this run:

- capture `listen/2/u110_capture.wav` (44.1 kHz; peak 0.796, **no clipping** -- listen/1 clips and
  must not be used for envelope work)
- voice parameters from `mame/error.log`, a MAME run of the same seven events on P-01
  selected from the front panel
- dry reference rendered at 32000 Hz, Fig. 4 filter applied, resampled to the
  capture rate, aligned by cross-correlation over the first 300 ms
- envelope sampled once per period of the note's fundamental

## Caveats

- **Sustain numbers are solid.** The dry render was validated against MAME's own
  output for every note: they agree to **0.2 dB** across the whole 3 s (see the
  emulator table below, which is flat at 0 until the emulator cuts the voice).
  So the sustain column really is the chip's doing and nothing else's.
- The release fit stops at the capture's noise floor (+6 dB). Fitting to the end
  of the analysis window instead fits an L-shape -- a real fall followed by several
  hundred ms of flat noise -- which is what made an earlier version of this table
  report 500-780 ms releases with R2 around 0.4.
- Note-on lands **0.18-0.28 s after the time in the capture log** -- the log records
  when the script sent the message. All times here are relative to the measured
  onset, not the log.
- P-01 here is the front-panel patch. The capture script sends a MIDI program
  change, which does not select the same thing (a program change of 0 produces
  different volume registers), so the two are not guaranteed identical.
